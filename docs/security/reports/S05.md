## Zmiany i kontrakty

1. `rate-limit.ts`: niezależne limity IP i konta/skrzynki; wspólny budżet skrzynki **6/h** łączy rejestrację, reset request i resend. Login ma krótkie/dłuższe okno zamiast trwałej blokady konta. Refresh/reset/weryfikacja przypisują ważny token do konta; rotacja nie zeruje budżetu.

| Operacja              | IP             | Konto/skrzynka |
| --------------------- | -------------- | -------------- |
| Login                 | 120/min        | 5/min, 30/15 m |
| Rejestracja           | 30/h           | 3/h            |
| Reset request, resend | osobno 60/h    | osobno 5/h     |
| Użycie resetu         | 60/15 m        | 10/15 m        |
| Weryfikacja           | 120/15 m       | 10/15 m        |
| Refresh               | 600/min        | 60/min         |
| Hasło, reauth         | osobno 60/15 m | osobno 10/15 m |
| Google                | 120/15 m       | —              |

2. Brak/błąd/timeout Redis uruchamia atomowy PostgreSQL UPSERT w `auth-throttle.service.ts`; odmowy nie przedłużają okna. Redis timeout 1,5 s nie jest sukcesem. Transakcja/blokada mają timeout. Awaria obu backendów: **503**, przekroczenie: **429**, zawsze Retry-After/no-store. Niezależne liczniki przy przełączeniu mogą dopuścić jeden dodatkowy budżet okna, nigdy nieograniczony fail-open. Nie ma samodzielnego fallbacku in-memory.
3. Klucze to HMAC-SHA256 z domeną/operacją i `AUTH_SECRET`, bez jawnych adresów/IP. Alarm `AUTH_RATE_LIMIT_UNAVAILABLE`: log i istniejące Sentry najwyżej raz/minutę/instancję; Sentry usuwa cały kontekst żądania/użytkownika. Istniejący dzienny cleanup usuwa wygasłe liczniki; bez nowej infrastruktury monitoringu.
4. IP: tylko pojedyncze `x-vercel-forwarded-for` przy `VERCEL=1`, walidacja i kanonizacja IPv6. Inne hosty/brak nagłówka: wspólny `unknown`, bez zaufania do dowolnego XFF. Podstawa: [oficjalny kontrakt ingress Vercel](https://vercel.com/docs/headers/request-headers). Nie wykonano produkcyjnego testu podszywania się; rzeczywisty odczyt nowym kodem pozostaje kontrolą po merge.
5. Rejestracja zawsze neutralny `201`, bez nadpisania istniejącego konta; oba warianty haszują hasło. Błędny login wykonuje bcrypt także bez konta/hasła. Rejestracja/recovery mają minimum 750 ms po walidacji; trwały outbox S04 pozostaje, odpowiedź nie czeka na dostawcę poczty (`queuedOnly`). Instrukcja PL/EN/DE/ES kieruje właściciela do skrzynki/logowania/resetu; poprawne hasło nadal umożliwia instrukcję potwierdzenia adresu.
6. Auth body: maks. 16 KiB rzeczywistych bajtów; e-mail 254 znaki, hasło 1024, token 256. Nieprawidłowy token resetu odpada przed haszowaniem. Wspólny `authFetch` w web/mobile respektuje Retry-After dla 429/503 bez automatycznych ponowień i przechowywania danych konta; refresh zachowuje tokeny przy czasowej niedostępności.
