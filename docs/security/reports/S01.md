## Zmiany

1. Uporządkowano `.cursorrules`: usunięto niepotwierdzone założenia o stacku i obowiązek formatowania całego repo. Wskazano istniejące Prisma, konfigurację aplikacji, izolację S00, zachowanie cudzych zmian i zakres przydzielonego zadania. Nie dodano nowych funkcji produktu.
2. `safeAuthRedirect` dopuszcza wyłącznie istniejące ścieżki panelu (z query/hash); pozostałe wartości kieruje do `/dashboard`. Odrzuca schematy, obce adresy, ukośniki odwrotne, kontrolne znaki i zakodowane ścieżki. AuthForm używa tego przed nawigacją.
3. Middleware sprawdza tylko brak cookie; nie uznaje jego obecności za ważną sesję i nie odsyła z publicznych stron auth. Layout nadal autoryzuje przez bazę. Przy nieaktualnej sesji przechodzi przez `/api/auth/session/clear`, który ponownie sprawdza sesję i czyści cookie wyłącznie dla nieaktualnej sesji. GET nie odwołuje ważnej sesji; odpowiedź ma `no-store`. `/api/auth/me` czyści cookie przy 401.
4. Wspólny `protectMutation` działa przed skutkami ubocznymi wszystkich obecnych POST/PUT/PATCH/DELETE API poza podpisanym webhookiem Stripe. Kontroluje Origin względem `NEXT_PUBLIC_APP_URL`, Fetch Metadata i Content-Type. Google callback pozostaje GET z istniejącą kontrolą state; nie zmieniono modelu łączenia kont.
5. Ujednolicono ustawianie i czyszczenie `sec_session`: HttpOnly, SameSite=Lax, Path=/, Secure na produkcji, bez Domain. Wylogowanie i usunięcie konta korzystają z tego samego helpera.
6. Dodano testy jednostkowe polityki oraz E2E logowania, przekierowań, trzech rodzajów nieaktualnych sesji, CSRF i mobile; fixtures są syntetyczne i usuwane z bazy.

## Kontrakt dla kolejnych etapów

`protectMutation(request, { bearer?, multipart? })` zwraca odpowiedź 403 (pochodzenie) albo 415 (typ treści), lub null. Błąd używa istniejącego tłumaczenia `auth.errors.generic`. JSON jest domyślnym formatem treści; multipart wolno włączyć wyłącznie dla skanowania paragonu. Puste żądania pozostają obsługiwane.

Web wymaga dokładnego Origin aplikacji. Cookie-free klient natywny bez Origin i Fetch Metadata może przesłać JSON, również login/refresh. Inny Origin wolno pominąć tylko w handlerze rzeczywiście korzystającym z Bearera (`bearer: true`), po jego weryfikacji i bez cookies. Sam nagłówek Authorization lub `x-client-platform` niczego nie dowodzi; błędny Bearer z cookies nadal podlega CSRF. Nie rozszerzaj CORS dla dowolnych origins. Przy wdrożeniu publiczny URL musi odpowiadać domenie aplikacji; aliasy i preview nie są automatycznie zaufane.

Rozważono `__Host-`: zachowano nazwę cookie, aby nie wylogowywać aktywnych użytkowników i nie wprowadzać podwójnego odczytu bez uzgodnionego rollout. Ewentualna osobna migracja wymaga nowej nazwy zapisu, wygaszenia starej przy zapisie/wylogowaniu i zakończenia odczytu starej po maksymalnym czasie sesji. S01 nie zmienia cyklu tokenów ani schematu bazy.

Wzorzec pochodzenia: [OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). Czyszczenie cookie w Route Handlerze: [Next.js cookies](https://nextjs.org/docs/app/api-reference/functions/cookies).
