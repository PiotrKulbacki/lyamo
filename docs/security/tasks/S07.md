# S07 — opcjonalne silniejsze uwierzytelnianie

Cel: dodać passkeys i opcjonalny drugi składnik wraz z bezpiecznym odzyskiwaniem. Zależność: S06. Następne: S08.

## Zakres

- Użyj utrzymywanych bibliotek WebAuthn/passkeys oraz TOTP, zamiast własnych algorytmów. Włączenie jest dobrowolne dla istniejących użytkowników.
- Passkeys: jednorazowy challenge, poprawny RP ID/origin, user verification, rejestracja dopiero po świeżym uwierzytelnieniu; kontrola listy/usuwania kluczy i bezpieczna obsługa ograniczeń urządzeń. Nie zakładaj, że licznik zawsze rośnie dla synchronizowanych passkeys.
- MFA: bezpieczne zapisanie sekretu TOTP z szyfrowaniem i zarządzaniem kluczem poza bazą, potwierdzenie aktywacji kodem, limity i ochrona replay. Nie dodawaj SMS jako domyślnego drugiego składnika.
- Login po pierwszym składniku tworzy wyłącznie krótki stan częściowego logowania. Sesja aplikacji/tokens powstają po wymaganym drugim składniku. Nie ufaj `mfaComplete` z klienta.
- Ustal spójną politykę dla hasła, Google i passkey: Google nie może omijać włączonego MFA; poprawnie zweryfikowany passkey może spełniać uzgodniony poziom bez zbędnych powtórzeń.
- Kody awaryjne są jednorazowe i haszowane; rotacja/wyłączenie MFA/usunięcie ostatniej metody wymaga świeżego potwierdzenia i powiadomienia. Sam reset hasła nie wyłącza MFA.
- Przetestuj web/mobile i Google-only. Nie oferuj w mobile niedziałającej metody; przy ograniczeniach platformy przedstaw działający, bezpieczny przebieg zamiast pomijania MFA.

## Pliki i skille

Auth API i ustawienia web/mobile, schemat Prisma, serwisy sesji i powiadomień S03–S04. Skill lyamo-supabase; oficjalne WebAuthn i dokumentacja wybranych bibliotek.

## Kryteria odbioru

- Rejestracja/użycie/odwołanie passkey i aktywacja/login/odzyskanie MFA działają.
- Przejęty stan częściowego logowania nie daje dostępu do API danych ani Stripe.
- Powtórny challenge/kod odzyskiwania i próby ominięcia MFA przez Google/reset/refresh są odrzucone; równoczesność sprawdzona na bazie.
- Utrata urządzenia ma opisany proces odzyskania; nie osłabia go dowolny administrator bez ustalonej procedury.
