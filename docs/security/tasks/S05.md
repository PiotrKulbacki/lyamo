# S05 — ochrona przed automatycznymi nadużyciami

Cel: chronić logowanie i odzyskiwanie kont także przy awarii Redis. Zależność: S04. Następne: S06.

## Zakres

- Limity per IP, konto/adres e-mail i operacja; oddzielne budżety dla logowania, rejestracji, wysyłki, resetu, weryfikacji i refresh. Nie stosuj jednego sztywnego limitu dla wszystkich działań.
- Ogranicz logowanie rozproszone po wielu IP oraz spam do jednej skrzynki. Preferuj progresywne opóźnienia/challenge zamiast łatwej do nadużycia trwałej blokady konta.
- Ustal tryb awaryjny Redis dla auth: brak nieograniczonego fail-open w produkcji, alarm i kontrolowana odpowiedź/fallback. In-memory limiter samodzielnie nie chroni rozproszonego serverless.
- Ustal wiarygodny adres klienta na rzeczywistym hostingu; nie ufaj dowolnemu `x-forwarded-for`. Użyj oficjalnych reguł Vercel/proxy. Nie deklaruj obejścia bez weryfikacji.
- Ujednolić neutralne odpowiedzi rejestracji, logowania i recovery oraz ogranicz różnice czasowe (np. dummy hash dla nieistniejącego użytkownika). Prawidłowy właściciel powinien otrzymać użyteczną instrukcję bez ujawniania danych osobie postronnej.
- Doprecyzuj walidację długości wejścia, rozmiaru body i tokenów przed kosztownym haszowaniem; obsłuż 429/Retry-After w web i mobile.

## Pliki i skille

`apps/web/src/lib/rate-limit.ts`, API auth, współdzielone schematy i klient mobile; kontrakt maili S04. Lyamo-vercel przy sprawdzeniu IP, zmiennych i logów; Upstash według oficjalnej dokumentacji.

## Kryteria odbioru

- Wiele IP nie omija limitu jednej skrzynki/konta; wspólna sieć nie blokuje nieproporcjonalnie zwykłych użytkowników.
- Awaria/brak konfiguracji Redis ma przewidywalne, ograniczone działanie i alarm.
- Nieistniejące i istniejące konto nie różnią się publicznym statusem/komunikatem; test timing ocenia rozbieżności, nie obiecuje idealnie stałego czasu sieci.
- Nie logujesz adresów e-mail wprost w kluczach/raportach, jeśli wystarcza skrót z odpowiednią ochroną.
